# wallet-billing

Сервис кошельков: счета пользователей, пополнение, списание, переводы, история операций. Фокус проекта — **корректная работа с деньгами при конкурентном доступе**: никаких потерянных обновлений, отрицательных балансов, дедлоков и двойных списаний.

> 🚧 Проект в разработке. Ниже в [дорожной карте](#дорожная-карта) отмечено, что уже сделано, а что впереди.

## Что уже работает

- Создание счёта, получение баланса
- Пополнение и списание с записью каждой операции в журнал `transactions`
- Защита от гонок при параллельных списаниях — доказана интеграционным тестом
- Clean Architecture: домен, сервисный слой, хранилище и транспорт разделены
- Graceful shutdown, health- и readiness-эндпоинты

## Быстрый старт

Нужны Docker и Go.

```bash
git clone https://github.com/zeroqual/wallet-billing.git
cd wallet-billing
cp .env.example .env

docker compose up -d
goose -dir migrations postgres "postgres://mazafaka:change_me@localhost:5432/billing?sslmode=disable" up

go run ./cmd
```

Сервис слушает `:8080`.

## API

| Метод | Путь | Тело | Описание |
|---|---|---|---|
| `POST` | `/v1/accounts` | `{"owner_id": "user-1"}` | Создать счёт (один на владельца) |
| `GET` | `/v1/accounts/{id}` | — | Счёт и баланс |
| `POST` | `/v1/accounts/deposit` | `{"id": "...", "amount": 100000}` | Пополнить |
| `POST` | `/v1/accounts/withdraw` | `{"id": "...", "amount": 70000}` | Списать |
| `GET` | `/healthz` | — | Процесс жив |
| `GET` | `/readyz` | — | База доступна, иначе `503` |

Суммы — целые числа в копейках (`100000` = 1000 ₽).

```bash
curl -X POST localhost:8080/v1/accounts -d '{"owner_id":"user-1"}'
curl -X POST localhost:8080/v1/accounts/deposit  -d '{"id":"<id>","amount":100000}'
curl -X POST localhost:8080/v1/accounts/withdraw -d '{"id":"<id>","amount":70000}'
curl localhost:8080/v1/accounts/<id>
```

```json
{
  "account": {
    "id": "6f1c...",
    "owner_id": "user-1",
    "balance": 30000,
    "created_at": "2026-11-21T12:00:00Z",
    "updated_at": "2026-11-21T12:00:05Z"
  }
}
```

| Код | Когда |
|---|---|
| `400` | Некорректный запрос: невалидный JSON или UUID, сумма ≤ 0, счёт не найден, счёт уже существует |
| `422` | Недостаточно средств |
| `500` | Внутренняя ошибка; подробности только в логах, клиенту не раскрываются |

## Ключевые решения

### Деньги — целые числа

Баланс и суммы хранятся в `bigint` в копейках, а не во `float`: у чисел с плавающей точкой `0.1 + 0.2 != 0.3`, и на миллионах операций копейки начинают «плыть».

### Атомарное списание вместо «прочитать → проверить → записать»

```sql
UPDATE accounts
SET balance = balance - $1, updated_at = now()
WHERE id = $2 AND balance - $1 >= 0
RETURNING ...
```

Проверка баланса и изменение происходят **одной командой**. Если два списания приходят одновременно, второе `UPDATE` ждёт блокировку строки и после неё заново проверяет `WHERE` уже на обновлённом балансе. Между проверкой и записью ничего не может вклиниться.

Сравнение подходов (проверено тестом ниже):

| Вариант | Результат при гонке |
|---|---|
| `SELECT balance` → проверка в Go → `SET balance = <значение>` | **lost update**: два списания уменьшают баланс один раз, деньги «появляются из ниоткуда» |
| `SET balance = balance - $1` без условия | деньги целы благодаря `CHECK (balance >= 0)`, но клиент получает `500` вместо понятного ответа |
| `SET balance = balance - $1 WHERE balance - $1 >= 0` | деньги целы, клиент получает `422 insufficient funds` |

Если `UPDATE` не нашёл строку, в той же транзакции проверяется существование счёта, чтобы отличить «счёта нет» от «не хватает средств».

### Защита на уровне базы

- `CHECK (balance >= 0)` — последний рубеж: даже при ошибке в коде база не сохранит отрицательный баланс.
- `CHECK (amount > 0)` и `CHECK (type IN (...))` в журнале операций.
- `UNIQUE (owner_id)` — один счёт на владельца.

### Журнал операций

Каждое изменение баланса пишется в `transactions` вместе с `balance_after` **в той же транзакции Postgres**. По журналу всегда можно объяснить текущий баланс и восстановить историю.

### Слои

```
api (Gin)  →  service  →  domain  ←  storage/postgres
```

- `domain` — сущности и доменные ошибки, без внешних зависимостей.
- `service` — сценарии; зависит от интерфейса репозитория, а не от pgx.
- `storage/postgres` — реализация на pgx; переводит ошибки базы в доменные (`pgx.ErrNoRows` → `ErrNotFound`, `23505` → `ErrAlreadyExists`).
- `api` — HTTP: разбор запроса, вызов сервиса, перевод доменных ошибок в коды ответа.

## Тесты

```bash
go test -race ./...          # все тесты, нужен запущенный Docker
go test -short ./...         # без интеграционных
```

**`TestWithdrawConcurrent`** — интеграционный тест на настоящем PostgreSQL (testcontainers, миграции применяются те же, что в проде):

1. счёт с балансом 500;
2. 100 горутин одновременно списывают по 10;
3. ожидается ровно 50 успешных списаний и 50 ответов «недостаточно средств», итоговый баланс 0 и 50 записей в журнале.

## Структура

```
cmd/                     точка входа
internal/
  api/                   HTTP: хендлеры, роутер, сервер
  config/                конфигурация из env
  domain/                сущности и доменные ошибки
  logger/                slog
  service/               бизнес-сценарии
  storage/postgres/      pgx: пул, репозиторий, интеграционные тесты
migrations/              миграции PostgreSQL
```
